# M1 — document formats

M1 adds the document layer and a format playground. The reactive cell editor,
autosave, undo, and inline cell UI are M2 work.

## Commands

```sh
zig build -Droc-source=/path/to/roc
zig build test
./zig-out/bin/roclet parse fixtures/documents/wall.roc
./zig-out/bin/roclet check fixtures/documents/wall.roc
./zig-out/bin/roclet run fixtures/documents/wall.roc
./zig-out/bin/roclet convert fixtures/documents/wall.roc --to markdown
./zig-out/bin/roclet convert notebook.md --to roc --output notebook.roc
./zig-out/bin/roclet convert notebook.roc --to roc --normalize
```

`parse`, `check`, and `run` return JSON. Conversion writes source to stdout, or
`--output`; diagnostics go to stderr with a file, line, and column. Existing files
require `--force`. Conversion returns status 1 for an invalid draft while still
returning its preserved source. Same-format conversion returns the exact input
bytes; `--normalize` explicitly requests a canonical export. Neither conversion
nor parsing evaluates notebook expressions. `check` uses the pinned compiler;
As of M3, the public CLI `run` command evaluates designated output roots using
Roclet's snapshot contract. The lower-level document protocol's `run` action
still invokes the generated entry for script-parity checks.

Relative imports and asset paths retain their spelling. Moving a document to a
different directory does not copy dependencies: the CLI refuses detected relative
reference relocation unless `--allow-relocation` explicitly requests text-only
relocation. Repair paths/copy assets when doing so.

The browser playground is `/web/formats.html`. It can open, inspect, convert,
check, run, and download files. Requests run in a WASM worker. Stop and edits during a running request terminate
the worker and discard its results; an idle worker retains only compiled engine
code for reuse. There are no remote execution
requests. A service worker/offline installation is still a later milestone.

The playground distinguishes **editing views** from **runnable exports**.
Convert format keeps final expressions and ordinary Roc definitions in the editor;
it does not insert the generated entry. Switching back without
an intervening edit restores the exact previous text, including whitespace.
Editing either representation invalidates the other saved view. New/opened
files clear both views, so an old document cannot reappear.

Markdown editing keeps Roc preamble/metadata in document state. `view` requests
return clean editing text; Markdown requests can carry this state as `context`.
Explicit metadata in pasted/opened Markdown takes precedence. Portable exports
include non-default configuration; the standard `app [main!] {}` preamble needs
no Markdown metadata. Reserved `rocPreamble` is not echoed back as redundant Roc
metadata. Unknown document fields remain preserved.

Preview runnable Roc exposes generated functions in a separate disclosure; it
never replaces the editing text. Save source exports the selected file format,
including the configuration needed to reopen it. Generated code is necessary in
a runnable Roc file even though it stays outside the editing view.

## Format decisions

This prototype uses the current format convention directly. Breaking format
changes are acceptable before production; legacy output-name aliases and
migration logic are out of scope.

- Roc recognizes column-zero `# %%` and `#%%` at compiler-confirmed top-level
  comment boundaries. Strings, interpolation, nested blocks, and incomplete
  delimiters do not manufacture boundaries.
- Comment-only cells infer Markdown. `code`, `markdown`, and `generated` override
  inference; empty cells default to code. An explicit empty Markdown cell stays
  Markdown. Canonical exports retain the kind of comment-only code cells.
- Code cells contain ordinary top-level Roc definitions, with one exception: a
  final expression may supply the cell result. A top-level `dbg` statement is
  diagnosed and preserved; use `dbg` inside a function or expression block.
- A cell selects at most one top-level `out_*` binding. A final expression gets
  `out_<id>` when its explicit ID contains only ASCII letters, digits, or
  underscores; otherwise it gets the first available name in `out_1`, `out_2`,
  `out_3`, and so on. Named collisions add a numeric suffix, such as `out_sum_2`.
  Other cells' explicit IDs are reserved before naming anonymous results.
  Canonical exports persist the binding in either format. Bare `out`, local
  bindings, and record fields do not select outputs. Non-final expressions and
  conflicting output choices produce diagnostics rather than speculative rewrites.
- Canonical exports omit `id=...` when the selected `out_*` binding implies
  exactly the same ID. For example, `# %% id=sum` followed by `1 + 2` exports as
  `# %%` followed by `out_sum = 1 + 2`. Other IDs and unknown attributes are
  retained, including IDs whose output name needed a collision suffix. Editing
  views preserve explicit attributes, and no-op saves preserve the exact source.
  Otherwise IDs derive from the selected output or declared names. They are not
  persistent identities, and no random ID or sidecar is inserted.
- Markdown uses CommonMark block parsing with GFM tables. Document-level `roc`
  fences are cells; `roc example`, nested fences, lists, quotes, and indented code
  remain prose. A Roc fence inside a Roc-format prose cell becomes `roc example`
  when exported, preserving its role as an example.
- Backticks are emitted with enough characters to contain the code safely;
  untouched Markdown retains its original fence style and whitespace.
- `<!-- %% -->` separates consecutive prose cells and protects output-shaped
  prose. Attributes use `<!-- %% id=... -->`. Empty prose uses
  `<!-- %% markdown -->`. Ordinary HTML comments stay ordinary comments.
- Literal marker comments gain one backslash only in document-level HTML-comment
  contexts. Import removes exactly that escape. Examples inside fences are not
  changed. A literal top-level `# %%` comment in a code cell uses the reversible
  Roc comment `# roclet:literal-marker "# %%"` on Roc export.
- A `text` fence, standalone image paragraph, or GFM table immediately after code
  is saved output. Ordinary prose ends that association. Saved output is always
  unverified and never input to evaluation.
- Roc text snapshots use `# =>`; richer output uses `# roclet:outputs` followed
  by JSON. Markdown emits text fences/images/tables and preserves other output
  kinds through explicit `<!-- roclet:outputs ... -->` metadata. Debug transcripts
  can use an explicit kind; ordinary text is not inferred to be a debug event.
- `<!-- roclet:document {"format":1,"rocPreamble":"..."} -->` preserves the
  preamble. Unknown document fields survive through a reserved Roc preamble
  comment. JSON in HTML comments escapes comment terminators.

## Debug statements and the generated entry

`dbg` uses ordinary Roc syntax inside a function or expression block:

```roc
out_1 = {
    area = width * height
    dbg area
    area + 1
}
```

Its messages still appear in the notebook's debug output. A standalone top-level
`dbg area` is not supported and is never wrapped in an invented helper function.
The only notebook syntax extension is a final cell expression, which becomes a
collision-free `out_*` definition in runnable exports.

The generated entry resides in `# %% generated` and prints selected outputs in
cell presentation order through a shared helper. It uses Roc string interpolation
(which requires `$`):

```roc
# %% generated
display! = |value| echo!("${Str.inspect(value)}\n")

main! = |_args| {
    display!(out_1)
    Ok({})
}
```

The helper accepts different output types and is omitted for notebooks without
outputs. User bindings named `display` or `display!` remain ordinary definitions;
the generator chooses `display_2!`, `display_3!`, etc. when needed, checking names
in both the cells and the preamble. Reopening and saving keeps this name stable.
Both the helper and `main!` stay out of editing views and Markdown exports.

The importer validates a narrow supported entry grammar before regeneration.
Arbitrary handwritten `main!` definitions, unexpected generated code, and multiple
generated entries are preserved and block execution. Validation checks the helper
body and requires calls to that helper with a single `out_*` binding. This prototype
recognizes the current generated structure, without migration for earlier forms.

## Implementation and maps

`core/Document.roc` owns segmentation, kinds, IDs, output selection, lowering,
metadata policy, validation, and encoding. It accepts explicit syntax facts and
has no filesystem or browser calls.

`compiler-adapter/syntax.zig` exposes the pinned Roc tokenizer and parser. A small
notebook parser entry accepts ordinary module declarations together with bare
expressions; it does not change the compiler's normal file grammar. The vendored
MIT-licensed MD4C 0.5.2 supplies Markdown structure and inline image recognition.
See `vendor/md4c/README.md` for its two integration changes.

`compiler-adapter/document.zig` calls the same Roc core in both hosts. It passes
input as JSON runtime arguments to one immutable Roc application and reads its
JSON result. It parses opaque JSON metadata fields without deciding
notebook policy. The first request compiles the application and copies only
its executable LIR tables and frozen constants into a private cache. Each later
call creates a fresh interpreter with new arguments. User notebooks and their
results are never cached by this mechanism. The browser prepares this engine at
startup and reuses the worker after completed operations. Stop, an in-flight edit,
or an engine error discards the worker and its cache. Ahead-of-time packaging
remains a possible improvement to first-load latency.

All model ranges and source maps are half-open UTF-8 byte offsets. `mappings`
relates the generated execution source to normalized cell text. Each cell's
`source_map` relates that text back to the saved body, including restored literal marker
comments. Document diagnostics compose both maps and include original-file
locations. The original source is retained separately for exact no-op saves.
Imported-module diagnostics remain in `evaluation.diagnostics` with their own
filename instead of being attributed to a notebook cell.

## Supported execution boundary

Document import/export preserves preambles, imports, paths, and drafts. Checking
and running through this adapter still use M0's in-memory echo platform; supplied
modules use the request's `modules` array. Automatic filesystem/package discovery,
arbitrary platforms, rich live values, and incremental evaluation are later work.
Use ordinary Roc to run exported applications in their own platform environment.
Simple top-level binding patterns are supported for output analysis; unsupported
patterns produce diagnostics and retain their source.

Document requests are limited to 256 KiB of source, with the underlying 1 MiB
compiled-source limit also applying to generated adapter requests. (Superseded:
the fixed core and notebook scratch budgets described here were later replaced by
growable arenas and an adaptively sized image buffer; see
`compiler-adapter/README.md`.) WASM memory growth is retained by an instance until its worker
is destroyed. The engine cache holds a compact copy of the executable program, not the compiler
arena; WASM itself retains its peak linear-memory allocation until Stop or reload.

## Verification

`zig build test` runs the existing M0 checks and the document contracts in
`tests/documents.json`, including round trips, real execution, and exact diagnostic
spans. It writes `artifacts/document-conformance.json` with complete native
requests/results and the artifact manifest.

Open `/web/document-conformance.html` to compare complete responses with WASM,
including source, model, diagnostics, maps, and events. The original M0 browser
suite remains at `/web/conformance.html` (superseded; see `web/document-conformance.html`). Document execution is also checked in
fresh workers, covering the allocation layout used by the playground and unsigned
WASM addresses above 2 GiB. Browser checks are separate from the
native build command. Initial validation results are recorded in `m1-validation.json`; the follow-up
round-trip/performance validation is recorded in `m1-format-fixes-validation.json`.
The simplified top-level syntax is covered by `m1-top-level-validation.json`.
